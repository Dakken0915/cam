## 项目面试问答

### 项目简介

&emsp;&emsp;本项目基于 i.MX6ULL 和 Linux，使用 C++、V4L2、OpenCV、Framebuffer、HTTP 和 POSIX 进程/线程技术，实现 USB 摄像头采集、LCD 显示、网页视频流、触摸拍照和人脸分析。系统支持 MJPEG/YUYV 输入、10/20/30 FPS 配置和 menuconfig 参数管理。

### 为什么普通光下约 10 FPS，强光下可以达到 30 FPS

&emsp;&emsp;主要原因是摄像头自动曝光。普通光照下，摄像头会延长曝光时间以保持画面亮度，单帧采集周期变长后实际帧率可能降到约 10 FPS；强光下曝光时间缩短，摄像头恢复到请求的 30 FPS。程序通过 V4L2 请求 30 FPS，但请求值不代表所有曝光条件下都能稳定输出 30 FPS。

&emsp;&emsp;排查时先停止应用，固定格式、分辨率和请求帧率，再使用以下命令连续采集 300 帧：

```sh
v4l2-ctl -d /dev/video1 \
  --set-fmt-video=width=640,height=480,pixelformat=MJPG \
  --set-parm=30 \
  --stream-mmap --stream-count=300
```

&emsp;&emsp;同时观察应用的 `CAP`。如果 `CAP` 随照度从 30 降到 10，问题发生在摄像头或驱动采集侧；如果 `CAP` 稳定而处理 `FPS` 下降，才需要分析应用处理路径。项目通过 `V4L2_CID_EXPOSURE_AUTO_PRIORITY` 提供帧率优先和亮度优先两种策略。

### 为什么选择多进程加共享内存

&emsp;&emsp;原先采集线程同时负责图像处理、LCD 缩放、像素转换和 framebuffer 写入，LCD 刷新耗时会阻塞视频处理。现在父进程负责摄像头采集、图像处理、HTTP 和人脸检测，LCD 子进程独立完成缩放和显示，通过共享内存传递 BGR 帧。

&emsp;&emsp;共享内存适合传递大图像，可以减少管道或 Unix Socket 的序列化和额外复制，并且能固定内存上限。多进程不会增加 i.MX6ULL 单核的总算力，主要收益是隔离 LCD 阻塞、降低主流程延迟。板端实测捕获约 30 FPS 时，主处理 `FPS` 约 17~21；`LCD` 单次绘制约 92~110ms，估算持续绘制能力约 9~11 次/秒，父子两个进程 CPU 占用合计约 50%；实际完成速率仍应看 `LCD_FPS`，不能据此证明真实上屏速率。

### 匿名共享内存和命名共享内存有什么区别

&emsp;&emsp;匿名共享内存通常使用 `mmap(nullptr, length, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0)` 创建。它没有文件名，映射关系通过父子进程继承传递，适合 `fork()` 后的进程间通信；当所有进程解除映射或退出后，内核自动回收这段内存。它的优点是生命周期简单、不会在 `/dev/shm` 留下对象、权限管理面小；限制是无关进程无法仅凭名称找到它，进程必须存在明确的继承或描述符传递关系。

&emsp;&emsp;命名共享内存通常使用 POSIX `shm_open()` 创建对象，配合 `ftruncate()` 设置大小、`mmap(..., MAP_SHARED, ...)` 映射，最后用 `shm_unlink()` 删除名字。对象有一个可被多个无亲缘进程使用的名称，因此适合独立启动的服务、跨程序通信和需要重新连接的场景；代价是需要处理名称冲突、权限、异常退出后的残留对象、大小调整和清理时机。System V 共享内存的 `shmget()`/`shmat()` 也属于命名或键值发现的共享内存，生命周期和清理规则与 POSIX 版本不同。

&emsp;&emsp;本项目选择匿名共享内存，因为 LCD 子进程由父进程直接 `fork()` 创建，不需要让其他程序发现或重连。`LcdProcess` 使用 `MAP_SHARED | MAP_ANONYMOUS` 一次性分配控制块、三个 BGR 槽位、进程共享互斥锁和计数型信号量；父子进程继承同一个虚拟地址映射，停止时由父进程 `munmap()`，不会留下命名对象。若未来把采集服务和 LCD 服务拆成两个独立启动的程序，再考虑 `shm_open()`，并同时设计权限、版本校验、超时恢复和 `shm_unlink()` 清理机制。

&emsp;&emsp;面试中不能只说“匿名更快”。两者映射后的读写性能主要取决于内存访问、缓存和同步方式，匿名与命名的核心差异是发现方式、生命周期和权限管理；本项目选择匿名是因为进程关系明确、资源清理简单，且能减少部署和异常恢复的管理成本。

### 为什么每个像素调用一次 memcpy 会增大总线开销

&emsp;&emsp;每个像素调用一次 `memcpy` 的问题不只是函数调用次数。以 1280x640 的画面为例，单帧约有 819200 个像素；旧实现对每个像素都要重新计算显存地址、准备一个临时像素值并执行一次极小长度的复制。即使编译器将 `memcpy` 内联，循环仍然包含大量边界计算和分散的小写操作；如果没有内联，还会额外产生调用和返回开销。

&emsp;&emsp;framebuffer 是通过 `mmap(MAP_SHARED)` 映射的设备内存，最终写入可能受到缓存属性、写缓冲和显示控制器总线规则影响。小块写入会让 CPU 难以把连续像素合并成较大的突发写传输，可能产生更多写缓冲提交、总线事务和等待；但不能简单说“一次 `memcpy` 就对应一次总线事务”，实际事务数量由 ARM 缓存属性、映射方式和驱动实现决定。即使总线能够合并，819200 次小复制带来的 CPU 指令和地址计算也会拖慢刷新。

&emsp;&emsp;本项目因此改为行级写入：先在普通内存的行缓冲中完成像素格式转换，再用一次 `memcpy` 写入整行。行缓冲写入可以利用连续内存和 CPU 缓存，显存侧也更有机会形成连续传输；显存行跨度、x/y 偏移和像素位域仍按 framebuffer 参数处理。这个优化降低的是小写操作和总线提交压力，不会自动消除 `cv::resize`、显存映射等待或 LCD 控制器刷新时间。

&emsp;&emsp;验证时不能只看进程 CPU 百分比，应比较稳定窗口中的 `LCD` 单次耗时、`LCD_FPS`、父子进程 CPU 和画面延迟。若行级写入后 `LCD` 明显下降，说明逐像素写入是主要瓶颈；如果变化不大，应继续拆分测量缩放、像素打包和显存拷贝。

### 项目如何使用双缓冲，DMA 是否由应用实现

&emsp;&emsp;打开 framebuffer 时检查 `yres_virtual` 和显存长度是否能容纳两个完整页面。满足条件时，LCD 子进程把下一帧写入后台页，驱动支持 `FBIO_WAITFORVSYNC` 时等待垂直同步，再调用 `FBIOPAN_DISPLAY` 把完整页面切到前台；如果驱动不支持虚拟页面或翻页 ioctl 失败，就回退单缓冲。双缓冲主要解决扫描和写入同时发生造成的撕裂，不会自动提高像素转换和显存写入速度。

&emsp;&emsp;DMA 不能仅通过通用用户态 framebuffer API 直接实现。LCD 扫描通常已经由内核 framebuffer 驱动配置 DMA，应用层负责向显存提供连续数据；如果要让应用提交 DMA 拷贝，必须使用具体 BSP 提供的 dmaengine、DMA-BUF 或私有 ioctl，并处理缓存一致性、缓冲区所有权、完成中断和超时。项目当前采用行缓冲、双缓冲和 VSYNC 翻页，保持对普通 fbdev 的兼容，启动日志中的 `double-buffer=yes/no` 可确认驱动能力。

### 缓存什么时候写回，LCD 如何拿到真值，共享内存是不是缓存

&emsp;&emsp;CPU 写入普通的 cacheable 内存时，通常先修改 cache line 并标记为 dirty，之后可能在 cache line 被替换、执行显式 clean/writeback、发生同步操作或由内核维护时写回内存。不能只凭“函数返回”判断外部 DMA 已经看到最新数据。写回和内存顺序是两个概念：写回把 dirty 数据推到内存，内存屏障保证前面的写操作不会被重排到后面的通知之后。

&emsp;&emsp;共享内存不是 cache。`mmap(MAP_SHARED | MAP_ANONYMOUS)` 建立的是多个进程对同一物理内存的映射；这段内存仍可能被每个 CPU 核心缓存。当前项目中，父进程先把 BGR 数据复制到共享槽位，再在互斥锁保护下把槽位改为 `READY`，最后 `sem_post()`；LCD 子进程 `sem_wait()` 后重新获取同一把进程共享互斥锁，再读取 `READY` 槽。POSIX 互斥锁和信号量提供跨线程/跨进程的同步和内存顺序，因此子进程不会在发布通知后读到父进程尚未完成的槽位内容。

&emsp;&emsp;LCD framebuffer 是另一类内存。它通过驱动的 `mmap` 映射，缓存属性由内核 framebuffer 驱动决定，可能是设备内存、写合并内存或其他架构相关属性，应用不能假设它和普通堆内存一样。当前程序只在完整后台页写完后调用 `FBIOPAN_DISPLAY`，驱动负责页切换和显示控制器访问；如果具体 BSP 使用非一致性 DMA 或提供 DMA-BUF 接口，就必须按 BSP 要求执行 cache clean、DMA fence 或同步 ioctl。没有这些接口时，不能在应用层自行“刷新 cache”来保证 LCD 真值。

### 行缓冲 memcpy 到 framebuffer 后，数据什么时候写回

&emsp;&emsp;`packedRow_` 是普通 `std::vector<uint8_t>`，通常属于 cacheable 的普通内存。CPU 把像素写入行缓冲时，先修改 CPU cache 中的 cache line；随后 `memcpy` 读取行缓冲，CPU 可以直接从自己的 cache 取到刚写入的数据，并不需要先把行缓冲完整写回 DDR。

&emsp;&emsp;`destination` 是 `/dev/fb0` 通过 `mmap` 返回的虚拟地址，不是可以直接解引用的物理地址。CPU 对这个地址执行的 store 会按照 framebuffer 驱动设置的页属性处理：

| 映射属性 | CPU 写入的典型行为 | 是否按普通 cache 写回 |
| --- | --- | --- |
| Device/uncached | 写操作直接经过互连到 framebuffer，通常不进入普通数据 cache | 否 |
| Write-combine | 写入先在写合并缓冲中聚合，再以较大突发提交 | 不按普通 dirty cache line 处理 |
| Normal cacheable | 可能进入 CPU cache 并变成 dirty，之后需要 clean/writeback 才能让非一致性 DMA 看到 | 是 |

&emsp;&emsp;所以不能回答“每次 `memcpy` 后一定发生 cache writeback”。当前程序没有手工执行 cache flush，而是依赖 `/dev/fb0` 驱动提供的 mmap 属性和 `FBIOPAN_DISPLAY` 实现。常见 fbdev 驱动会把 framebuffer 映射成设备内存或 write-combine 内存，并在页翻转路径中处理必要的写入顺序；但这不是仅由 C++ `memcpy` 保证的。`msync()` 也不是通用的 framebuffer DMA 同步接口，不能替代 BSP 提供的 DMA-BUF sync 或专用 ioctl。

&emsp;&emsp;当前一帧的顺序是：CPU 从 cache 读取行缓冲，写入后台 framebuffer 页；全部行完成后，再执行 VSYNC 等待和 `FBIOPAN_DISPLAY`。页翻转只能在驱动已经保证后台页写入对显示控制器可见时才安全。若换成非一致性 DMA 拷贝，必须在提交 DMA 前 clean 源 cache，在 DMA 完成 fence/中断后才能翻页，不能只依赖 `memcpy` 返回。

### 为什么使用行缓冲，不使用整片软件缓冲

&emsp;&emsp;行缓冲只保存当前要写入的一行像素，完成 BGR 到 RGB565、24 位或 32 位格式转换后立即复制到 framebuffer。整片软件缓冲需要保存完整的目标画面，例如 1280x640 RGB565 约 1.6 MiB，32 位则约 3.2 MiB；如果还要保留缩放图、共享槽位和硬件双缓冲，内存会继续增加。i.MX6ULL 的内存容量和带宽都有限，实时视频不需要保留一张等待后续修改的完整软件画面。

&emsp;&emsp;画面不是全屏时，整片软件缓冲还会为左右或上下黑边分配和复制空间；行缓冲只按目标行宽分配，实际只处理居中的有效 `rowBytes`，黑边由页面清屏完成。当前 640x480 输入在 1280x640 LCD 上会产生留白，行缓冲不会为每一帧额外保存这些留白区域。代价是行缓冲不能像整片软件缓冲那样随意回读、合成或多次修改整张图，因此按钮和统计面板需要在页面渲染阶段继续绘制。

&emsp;&emsp;硬件双缓冲和行缓冲解决的是不同问题：双缓冲需要两页完整 framebuffer 显存来避免扫描撕裂，行缓冲只是 CPU 侧的临时转换空间。项目保留硬件双缓冲的两页显存，但没有再增加一份完整的软件目标帧。

### DMA、双缓冲、行缓冲和 cache 的数据流水线

&emsp;&emsp;当前路径可以按以下顺序理解：

```text
摄像头/解码
    -> 普通 cacheable BGR 内存
    -> 逐行格式转换到行缓冲
    -> 连续写入 framebuffer 后台页
    -> 页面写完并完成内存顺序约束
    -> FBIO_WAITFORVSYNC（驱动支持时）
    -> FBIOPAN_DISPLAY 翻到前台页
    -> LCD 控制器 DMA 扫描前台页
```

&emsp;&emsp;行缓冲阶段的写入一般发生在 CPU cache 中，写满一行后再复制到 framebuffer 映射区域。硬件双缓冲要求 CPU 始终写后台页，LCD DMA 始终读前台页；只有后台页完整、可见性和顺序得到保证后才翻页。翻页后 CPU 立刻可以写另一页，LCD 不会读到正在修改的页面，因此减少撕裂。

&emsp;&emsp;如果使用专用 DMA 做“行缓冲到 framebuffer”的拷贝，流程会变为：先准备并 clean 行缓冲对应的 cache line，提交 DMA 描述符，等待 DMA 完成中断或 fence，确认后台页的目标范围已写完，再执行 VSYNC/页翻转。DMA 完成前不能复用行缓冲，也不能把后台页提前交给 LCD。逐行启动 DMA 还会增加描述符和中断开销，通常需要合并多行或整帧传输才有收益；这也是当前工程不凭空加入通用 DMA 设备节点的原因。

&emsp;&emsp;面试中可以这样概括：共享内存解决进程间传递，cache 一致性解决 CPU 和外部设备看到的内容，行缓冲解决 CPU 转换空间和小写入开销，双缓冲解决显示扫描与写入的并发，DMA 负责在具体硬件接口支持时搬运数据。它们是流水线上的不同层次，不能互相替代。

### 当前代码中共享内存、行缓冲和 framebuffer 的实际关系

&emsp;&emsp;当前实现不是“行缓冲写入共享内存，再把共享内存映射到物理地址”。父进程通过 `LcdProcess::publish()` 把完整 BGR 帧复制到三槽匿名共享内存；复制时按源图像的行跨度逐行复制，但这只是处理 `cv::Mat` 的 stride，不是 framebuffer 行缓冲。共享内存由 `start()` 在 `fork()` 前创建并映射，子进程继承同一映射，后续每帧不会重新 `mmap`。

&emsp;&emsp;LCD 子进程拿到共享槽位后，`cv::Mat` 直接把槽位地址包装成 BGR 输入，调用 `FramebufferSurface::render()`。该函数先用 OpenCV 生成缩放图，再使用自己的 `packedRow_` 行缓冲：每次处理一行，把 BGR 像素转换成 framebuffer 格式，然后一次 `memcpy` 到 `/dev/fb0` 的 framebuffer 虚拟映射区域。这个目标地址不是应用直接操作的物理地址，物理显存由内核 `mmap` 建立映射。

&emsp;&emsp;每帧通常只更新有效画面矩形的行，不是每次都复制整个屏幕：全屏比例时写 `height` 行、每行 `width * bytes_per_pixel` 字节；保持比例显示时只写居中的图像区域，黑边只在每个页面首次使用或输入几何变化时清屏。照片按钮和统计面板是额外的小区域像素写入。

&emsp;&emsp;启用硬件双缓冲时，子进程把这些行写入后台页；整帧写完后调用 VSYNC 和 `FBIOPAN_DISPLAY`，一次翻转整页。LCD 控制器随后从前台页扫描，因此“行级写入”发生在后台页，“整屏切换”发生在页翻转时，两者不是重新映射或逐行触发 DMA。

### 如何区分摄像头、图像处理和 LCD 瓶颈

&emsp;&emsp;项目分别统计三个指标：

| 指标 | 含义 |
| --- | --- |
| `CAP` | 采集线程从 V4L2 成功获取帧的速率 |
| `FPS` | 图像处理完成并进入 HTTP 输出队列的速率 |
| `LCD` | LCD 子进程刷新次数和平均刷新耗时 |

&emsp;&emsp;`CAP` 和 `FPS` 同时约 10，说明摄像头或驱动实际只交付约 10 帧；`CAP` 约 30 而 `FPS` 约 10~20，说明解码、JPEG、人脸分析或队列处理跟不上；`CAP/FPS` 约 30 而 `LCD_FPS` 约 9~11，说明显示路径是瓶颈。`LCD` 字段是单次显示耗时，不能当作显示帧率。

&emsp;&emsp;排查时通过 `--no-lcd`、降低分辨率、降低人脸检测频率和切换 MJPEG/YUYV 逐项对照，避免把应用处理瓶颈误判为摄像头输出上限。

### 共享内存如何保证并发安全

&emsp;&emsp;共享内存使用三个槽位，状态按以下顺序流转：

```text
FREE -> WRITING -> READY -> READING -> FREE
```

&emsp;&emsp;父进程取得空闲槽后写入 BGR 帧和序号，再标记为 `READY`；LCD 子进程只消费最新的 `READY` 槽，完成显示后释放槽位。没有空闲槽时丢弃旧的 `READY` 帧，避免显示延迟持续积累。

&emsp;&emsp;共享控制块使用 `PTHREAD_PROCESS_SHARED` 的 pthread 互斥锁保护共享槽位；新帧通知使用进程共享的计数型信号量。LCD 子进程在其他应用线程创建前通过 `fork` 启动，避免继承处于锁定状态的 C++ 或 OpenCV 线程资源。

&emsp;&emsp;当前 LCD 通知使用进程共享的计数型 POSIX 信号量 `sem_t`：父进程发布 READY 帧后调用 `sem_post()`，子进程使用 `sem_wait()` 阻塞等待。信号量只表示有通知，槽位状态仍由进程共享的 pthread 互斥锁保护；若旧帧被丢弃导致通知计数多于 READY 槽，子进程会重新扫描并继续等待，不会直接假设一定存在可读帧。停止时父进程设置停止标志并 `sem_post()` 唤醒子进程。

### 如何使用工具定位实际帧率问题

&emsp;&emsp;首先停止应用，避免摄像头设备被占用：

```sh
pkill cam_server_arm
```

&emsp;&emsp;然后按以下顺序排查：

- 使用 `v4l2-ctl --list-formats-ext` 查看摄像头支持的格式、分辨率和帧率。
- 使用 `--set-fmt-video` 和 `--set-parm=30` 显式设置测试条件。
- 使用 `--get-fmt-video --get-parm` 查看驱动实际回报的参数。
- 使用 `--stream-mmap --stream-count=300` 测量完整采集窗口。
- 运行应用时对照启动日志、`[Stats] CAP/FPS/LCD` 和 `top -H`。
- 使用 `dmesg` 检查 USB 断开、UVC 重枚举和驱动错误。
- 使用 `lsusb -t` 确认 USB 链路速率和 Host 状态。
- 使用 `--list-ctrls` 检查曝光和自动曝光优先级控制。

&emsp;&emsp;所有对照必须固定摄像头格式、分辨率、曝光状态和 USB 连接。`driver selected: 30 FPS` 只能说明 ioctl 接受了参数，最终结论必须以连续采集结果和应用 `CAP` 为准。

### 项目优化结果

&emsp;&emsp;MJPEG 模式下直接复用摄像头压缩数据，减少应用层软件 JPEG 编码；LCD 使用独立进程和共享内存，降低显示刷新对主处理线程的阻塞；人脸检测使用异步线程和抽样策略，避免检测任务积压。

&emsp;&emsp;已有一组板端日志中，摄像头捕获约 30 FPS，主处理 `FPS` 约 17~21，`LCD` 单次绘制约 92~110ms，父子进程 CPU 占用合计约 50%。这里的 17~21 是主处理速率，不能写成 LCD 刷新速率；92~110ms 只能估算持续供帧时的绘制能力，实际完成速率应读取同窗口 `LCD_FPS`。这些数据不能直接视为当前驱动版本或所有配置下的固定性能。

### LCD 帧率怎么检测，程序如何知道 DMA 完成，统计值是否真实

&emsp;&emsp;首先区分三个量：面板扫描频率、应用绘制完成速率、屏幕实际呈现不同视频帧的速率。LCDIF 可以按面板时序反复扫描同一页，即使程序一秒都没有更新画面，面板仍可能保持例如 60Hz 的扫描；程序每秒更新 10 张图时，看到的视频内容仍只有约 10 FPS。这里的 60Hz 只是示例，1024×600 分辨率本身不能确定刷新率。

| 要测的量 | 测量方法 | 目前是否直接统计 |
| --- | --- | --- |
| 应用 LCD 绘制完成速率 | 成功返回的 `display.render()` 次数除以实际经过的秒数 | 是，日志 `LCD_FPS` |
| 面板扫描频率 | 连续统计每个 VSYNC 或帧完成事件，或测量面板 VSYNC 信号 | 否 |
| 不同视频帧真正上屏的速率 | 把帧序号与硬件页面生效事件关联；用高速录像核对屏幕帧号 | 否 |

&emsp;&emsp;代码依据是 [renderLoop()](../src/lcd_process.cpp) 与 [encodeLoop()](../src/main.cpp)：子进程使用 `steady_clock` 测量一次 `display.render()` 的墙钟耗时，成功返回后增加共享 `renderCount`；父进程在约一秒的窗口通过 `takeRenderStats()` 取走并清零计数，计算 `LCD_FPS = renderedFrames / elapsed`。`LCD=...ms` 是这些调用的平均耗时，不包括前面的 `sem_wait()`，也不包括后面的统计面板 `renderStats()`，所以不能简单用 `1000 / LCD毫秒数` 代替实测 `LCD_FPS`。窗口取样有轻微边界偏差，稳定长窗口更有代表性。

&emsp;&emsp;应用并不知道每一次 DMA 读内存事务何时发生，也不需要逐次接收通知。[presentPage()](../src/framebuffer.cpp) 在双缓冲下先调用 `FBIO_WAITFORVSYNC`，再调用 `FBIOPAN_DISPLAY`；仓库 [LCDIF 驱动](../drv/lcd_drv.c) 将下一页 DMA 地址写入 `NEXT_BUF`，LCDIF 在 VSYNC 或当前帧完成时产生硬件 IRQ，`lcdif_irq_handler()` 调用 `complete()`，唤醒阻塞在 `wait_for_completion_timeout()` 的 ioctl。通知路径是“LCDIF 硬件事件 → 内核中断处理 → completion 唤醒 → 用户态 ioctl 返回”，不是 DMA 每取一块数据就调用应用。

&emsp;&emsp;目前只能严格把 `LCD_FPS` 称为应用绘制完成速率。单缓冲、缺少 IRQ、异步翻页或翻页失败后回退时，函数返回不等于新页面已经完整扫描到屏幕。即使启用 IRQ，当前驱动也只等待通用帧完成事件，没有把待翻页的帧序号与 `CUR_BUF` 实际生效地址逐次核对；因此不能仅凭返回成功证明这一张新图已经完整可见。驱动的 `current_page` 是提交时更新的软件状态，同样不能作为硬件已生效的独立证据。

&emsp;&emsp;验证方法是：先确认板端加载的驱动与仓库版本一致，检查启动日志的双缓冲和 IRQ 能力，再连续采样 VSYNC/帧完成时间戳；需要测真实上屏时，在图像中叠加唯一帧号，记录提交帧号、目标页地址和硬件实际切换的对应关系，并用高速录像核对。当前驱动只在等待期间开启对应中断，不能直接用 `/proc/interrupts` 的增量当作面板扫描次数；它可用来检查中断是否工作，精确扫描统计应另设持续启用且正确清状态的计数路径。这是验证建议，当前没有新增该统计接口或取得板端实测。

&emsp;&emsp;对于普通逐行扫描，理论刷新率可按 `实际像素时钟 / (水平总像素 × 垂直总行数)` 估算，总数包含有效区、前后肩与同步脉冲。应核对实际时钟，不能只取设备树请求值；时序计算验证的是扫描配置，也不能证明应用没有重复显示旧帧。fbdev 的几何、时序和 mmap 接口可参阅 [Linux Framebuffer 文档](https://docs.kernel.org/fb/framebuffer.html)。

### CAP 足够高，为什么 LCD 子进程帧率仍低，而且 CPU 没有跑满

&emsp;&emsp;“子进程只负责 LCD”表示职责独立，不表示每一刻都在执行像素计算。先看实际供帧：父进程还要取队列、解码和发布共享帧；MJPEG 模式下 `renderFrame` 受 `--lcd-interval N` 控制，依据的是处理到的帧数而不是 `CAP`。处理 30 FPS、`N=3` 时只发布约 10 帧/秒，处理 18 FPS 时只发布约 6 帧/秒。YUYV 当前不使用这个抽样限制。共享三槽只消费最新 READY 帧，也会主动跳过旧帧，保证低延迟而非逐帧播放。

&emsp;&emsp;然后看子进程每帧的完整路径：等新帧、取得槽位、`cv::resize`、BGR 像素打包、显存行拷贝、按钮绘制、等待 VSYNC、提交翻页并等待帧完成、更新统计及绘制统计面板。无数据时 `sem_wait()` 睡眠；等锁、等 VSYNC、等帧完成时也可能睡眠；进程可运行但父进程或其他任务占用单核 CPU 时，还要等调度。i.MX6ULL 是单核，多进程不能增加 CPU 核心数。

&emsp;&emsp;例如一轮更新经过 100ms，其中真正记账到子进程的 CPU 时间只有 20ms，其余 80ms 在睡眠或等调度，那么约 10 FPS 与约 20% CPU 完全可以同时出现。这只是解释统计含义的例子，不能由现有日志断言实际等待了 80ms。CPU 利用率应看整个一秒窗口中的运行时间，不等于渲染函数的墙钟耗时占比。

&emsp;&emsp;特别注意：CPU 执行 store 时因 DDR、互连或显存写缓冲受阻，若线程仍在运行，停顿周期通常仍算 CPU 时间，`top` 不会自动把它算成睡眠。因此“显存慢，所以 CPU 一定低”不成立；帧率低且 CPU 低，应优先找供帧间隔和阻塞等待，再用数据确认是否存在内存带宽瓶颈。

&emsp;&emsp;当前应用先等 VSYNC，再进入会等待帧完成的翻页 ioctl，存在两个硬件等待点，可能额外跨过刷新周期。假设面板为 60Hz，一个周期约 16.7ms，等待会对完成速率产生量化影响；两个等待是否增加一个或多个周期取决于提交时机和硬件行为，不能直接认定固定减半。若怀疑这里限速，应分别记录两个 ioctl 的耗时，确认后再考虑合并等待策略。

&emsp;&emsp;定位时固定格式、分辨率、曝光和人脸配置，MJPEG 可先设 `--lcd-interval 1`，同时记录发布次数、READY 丢弃次数与完成次数，逐项测量 `sem_wait`、缩放、打包、拷贝和两个 ioctl。阶段墙钟用 `steady_clock`，渲染线程 CPU 时间可用 `CLOCK_THREAD_CPUTIME_ID`；配合 `top -H`、`/proc/<子进程PID>/wchan` 和 `strace -tt -T -e trace=futex,ioctl -p <子进程PID>` 区分等待位置。工具需板端支持，`strace` 会扰动时序，最终性能应关闭跟踪后复测。

### DMA 已经负责取显存，为什么行缓冲更快，物理地址是否绕过 cache

&emsp;&emsp;这里有两段传输：“CPU 把新画面写进 framebuffer”和“LCDIF DMA 从 framebuffer 读取并扫描输出”。当前行缓冲优化的是前一段，后一段并没有替 CPU 完成缩放、格式转换或 framebuffer 写入。DMA 即使一直扫描，CPU 没及时准备好新图时也只能重复读旧内容。

```text
共享内存 BGR 帧
    → CPU 缩放与格式转换
    → 普通内存 packedRow_（一行）
    → CPU memcpy 到 framebuffer 后台页
    → 同步提交页面
    → LCDIF DMA 读取该页并输出面板
```

&emsp;&emsp;逐字节或逐像素直接写显存，会把像素计算与大量细碎的目标 store 交错，还可能重复进行地址计算、边界检查和小 `memcpy`。行缓冲先在普通可缓存内存里连续打包，再一次复制整行，让显存写入更连续，更有机会使用合适宽度的 store、写合并和突发传输。以全屏 1024×600 RGB565 为例，每帧约写 1.17 MiB，逐字节处理会执行约 123 万次目标字节写；行缓冲只需发起约 600 次行复制，但每次复制内部仍包含多条 store，绝不是只发生 600 次总线传输。保持比例时实际图像区域可能更小，按钮与统计面板还会增加写入。

&emsp;&emsp;“一次小 memcpy 对应一次总线事务”或“写一个字节就 flush 一次 cache”都不准确。实际效果由编译器、`memcpy` 实现、地址对齐、映射属性和 ARM 写缓冲决定；直接顺序写入也可能被合并。行缓冲还增加了临时内存读写，若原先已经是高效的连续宽 store，它未必更快，所以收益必须在板端相同条件下比较拷贝耗时与完成帧率。

&emsp;&emsp;应用操作的是 `mmap()` 返回的用户虚拟地址，MMU 把它翻译为相应内存地址；并不是应用在 C++ 中直接解引用物理地址。cache 是否参与由映射的内存属性决定，而非“它最终对应物理内存”决定。普通堆、共享内存最终也对应物理内存，照样可以走 cache。DMA 地址与 CPU 物理地址在一般平台上还可能有地址转换，不能把三种地址混用。

&emsp;&emsp;对仓库这版驱动，证据比泛泛讨论更明确：显存使用 `dma_alloc_wc()`，用户映射通过 `dma_mmap_wc()`，即请求写合并属性；这类映射通常不按普通 write-back 数据 cache 的 dirty line 方式处理 CPU 写入。`packedRow_` 则是普通 `std::vector` 内存，CPU 可以从自己的 cache 读出刚打包的数据，无需先把整行写回 DDR。WC 也不表示零等待或无限带宽，提交页面前仍需要驱动保证 CPU 写入与设备访问的顺序。板端若加载其他 BSP 驱动，必须重新检查它的 mmap 实现，不能直接套用仓库结论。相关约束见 [Linux DMA API 文档](https://docs.kernel.org/core-api/dma-api.html)。

### 信号量在进程间做什么，不用它子进程怎样知道有新数据

&emsp;&emsp;共享内存提供“双方能访问同一份图像”，信号量提供“发布后通知，没通知时睡眠”，互斥锁和槽位状态提供“安全取得、发布、释放槽位”。它们分别解决数据存放、事件通知与并发协调，不能互相替代；本项目的信号量不是 LCD DMA 完成通知，后者由驱动 IRQ 和 completion 处理。

&emsp;&emsp;初始化为 `sem_init(&readyFrames, 1, 0)`：第二个参数非零表示跨进程共享，初始计数为 0，而且 `sem_t` 本身放在匿名共享映射内。父进程先在锁内把槽位设为 WRITING，解锁后复制像素，再加锁改为 READY，解锁后 `sem_post()` 增加通知计数。子进程 `sem_wait()` 在计数为 0 时阻塞，有计数时减一并继续；随后在互斥锁内重新扫描 READY，取得最新槽并标记为 READING，读完再释放 FREE。父进程不能改写 READING 槽，所以大块像素复制和显示过程可以放在锁外。进程共享互斥锁的发布与获取也为普通共享内存建立同步顺序，不能只用 `volatile` 标志替代。

&emsp;&emsp;信号量会保存通知计数。即使父进程先 `sem_post()`、子进程稍后才 `sem_wait()`，通知也仍在，不会因为当时没人睡眠而直接丢失。反过来，一次通知也不对应一张必须读取的图：本项目会覆盖或丢弃旧 READY 帧，计数可能多于剩下的 READY 槽，子进程必须每次醒来都检查真实状态，无帧就继续循环，不能把计数当作队列长度。长期过量通知也可能增加空扫描开销；通知合并属于后续设计，需要额外处理唤醒竞态，当前没有实现。

&emsp;&emsp;没有信号量并非不能工作，但必须换一种发现机制：不断加锁检查 READY 是忙轮询，响应快但浪费 CPU；检查后睡眠一段时间是定时轮询，省 CPU 但增加延迟；管道或 `eventfd` 可以提供可阻塞、可 `poll` 的通知；进程共享条件变量也可以配合同一把互斥锁和 `while` 条件循环使用。仅把共享标志设成 READY，不会自动把一个睡眠的子进程唤醒；用“先检查，再无保护地睡眠”的写法还可能漏掉中间到达的通知。

&emsp;&emsp;停止时同样要通知：父进程在锁内设置 `stopping`，再 `sem_post()` 唤醒子进程，子进程醒来先检查停止标志再退出；`sem_wait()` 被信号中断返回 `EINTR` 时当前代码会重试。信号量规则可核对 [sem_init 手册](https://man7.org/linux/man-pages/man3/sem_init.3.html) 与 [sem_wait 手册](https://man7.org/linux/man-pages/man3/sem_wait.3.html)。

### CPU 只有约一半占用，MJPEG 也能直接复用，为什么处理 FPS 明显低于 CAP

&emsp;&emsp;这个质疑成立：如果确认整机单核 CPU 确实持续有空闲、`raw` 队列持续有帧、处理线程可运行且没有限流，那么它通常应该获得更多 CPU 时间继续处理，不能只用“采集和处理不在一个线程”解释差距。但“父子进程合计约 50%”只说明这两个进程在采样窗口内的平均占用，不能证明整机有 50% 空闲，也不能说明空闲时处理线程恰好有工作可做。需要同时核对同一稳定窗口的整机 idle、其他任务、IRQ/softirq 与具体线程状态。CPU 统计的含义可参阅 [Linux /proc 文档](https://www.kernel.org/doc/html/latest/filesystems/proc.html)。

&emsp;&emsp;MJPEG 的“直接用”针对 HTTP 流和照片：摄像头已经提供 JPEG 压缩字节，应用不用再编码一次，浏览器负责解码显示。framebuffer 接收的却是 RGB565 等原始像素，不能直接写入 JPEG 压缩字节；人脸检测也需要像素图。当前 [encodeLoop()](../src/main.cpp) 在处理线程内先执行以下步骤，之后才发布 JPEG：

| 阶段 | MJPEG 模式下实际工作 | 是否包含在日志 `JPEG` 耗时中 |
| --- | --- | --- |
| 取得输入 | `raw.take()` 取帧，队列空时阻塞 | 否 |
| 按需解码 | LCD 或人脸抽样命中时，调用 `cv::imdecode()` 得到 BGR；两者同时命中只解码一次 | 否 |
| 提交人脸任务 | 命中人脸抽样时，`submitSelected()` 先 `bgr.clone()`，再通知异步检测线程 | 否 |
| 发布 LCD 帧 | 命中 LCD 抽样时，`lcd.publish()` 取得槽位并逐行复制完整 BGR 帧，再通知子进程 | 否 |
| 检查 LCD 存活 | `waitpid(..., WNOHANG)` 检查子进程状态 | 否 |
| 复用 JPEG | `encoded.data = std::move(frame.data)`，通常转移 vector 缓冲区所有权 | 是 |
| 输出与统计 | 放入 `jpeg` 队列、计数；统计时访问共享锁并可能写诊断日志 | 否 |

&emsp;&emsp;所以 `JPEG=0.004ms` 只能说明这一步没有重新压缩、移动成本很小，不能说明整个处理循环只用 0.004ms。640×480 BGR 图约为 0.88 MiB，每次 LCD 发布都要复制这份未压缩数据；命中人脸抽样还要额外 clone。真正的人脸检测在后台线程，LCD 缩放、像素打包、显存写入及 VSYNC 等待在子进程，但它们仍与父进程共享单核 CPU 和内存带宽。`cv::imdecode()` 的内存输入解码语义见 [OpenCV 官方说明](https://docs.opencv.org/4.x/d4/da8/group__imgcodecs.html)。

&emsp;&emsp;当前统计也要分清：`CAP` 在成功取得摄像头帧后增加；`FPS` 在处理线程完成上述路径并调用 `jpeg.push()` 后增加，不是浏览器播放速率，也不等待 LCD 上屏。主线程之后才调用 `HttpServer::updateFrame()`，在锁内复制最新 JPEG；HTTP 慢客户端不会通过满队列直接阻塞处理线程，因为 `BoundedQueue::push()` 在满载时丢弃旧帧，只可能短时等待队列互斥锁。当前源码的 `raw`、`jpeg` 容量均为 3，应以实际运行版本为准。

&emsp;&emsp;对稳定、无错误退出的流水线，可按“采集数 ≈ 已处理数 + raw 丢弃数 + 待处理/处理中数量的变化”核对。若连续十秒 `CAP≈30`、`FPS≈18`，差约 120 帧，三帧队列无法长期保存这个差额，必然有大量采集帧在处理前被丢弃。应直接在 raw 队列满载位置记录丢帧数验证，而不是用有限队列中的积压解释持续差距。`--lcd-interval` 只跳过部分帧的 LCD 解码/发布，并不会故意把主处理 `FPS` 除以该间隔；LCD 共享槽丢帧和 jpeg 输出队列丢帧也不直接扣减已经计入的主处理帧数。

&emsp;&emsp;平均 CPU 空闲与短时丢帧可以同时存在。例如处理线程偶尔在同步日志输出上阻塞 200ms，采集侧仍可能到达约 6 帧，容量 3 的 raw 队列会丢旧帧；随后处理线程把剩余帧快速取完又等待新帧。之后空闲的 CPU 时间无法找回已丢弃的数据。这只是说明短时停顿与有限缓冲如何产生差距，并非本项目已确认存在 200ms 日志阻塞。长耗时解码、其他任务抢占、内存分配或锁竞争也需要按时间线核对，不能只拿一个平均 CPU 百分比下结论。

&emsp;&emsp;尤其不能直接套用“LCD 在等 VSYNC，所以主处理 FPS 低”。当前 `publish()` 不等待子进程绘制完成，子进程也没有在缩放或等待 VSYNC 时持有共享互斥锁；没有 FREE 槽时父进程优先覆盖旧 READY 槽，而不是等 LCD 消费。只有实际 CPU/带宽竞争、短时共享锁等待等间接影响需要测量。正常情况下父进程也不等待后台人脸检测完成，只承担提交复制和锁的成本。

&emsp;&emsp;定位时先做 MJPEG 纯转发基线，确认启动格式确实为 MJPEG，并保持分辨率、曝光、HTTP 客户端数量一致：

```sh
# 纯压缩数据转发：不再为 LCD 或人脸解码
CAM_DEBUG=1 ./cam_server_arm --device /dev/video1 --format mjpeg \
  --no-lcd --no-touch --no-face

# 只增加 LCD 路径，排除人脸分析
CAM_DEBUG=1 ./cam_server_arm --device /dev/video1 --format mjpeg \
  --fb /dev/fb0 --no-touch --no-face --lcd-interval 1

# 只增加人脸路径，排除 LCD 路径
CAM_DEBUG=1 ./cam_server_arm --device /dev/video1 --format mjpeg \
  --no-lcd --no-touch --face-interval 30
```

&emsp;&emsp;三组应依次运行，上一组退出后再启动下一组；第三组还要确认模型加载成功，否则实际没有启用分析。若纯转发下 `FPS` 接近 `CAP`，再开启某一路后差距明显，才有证据缩小到对应支路；若纯转发也明显低于 CAP，就应优先查输入队列、调度/锁、日志输出和统计版本，不能归因于根本未执行的解码。以上命令只提供对照方法，本次没有取得板端运行结果。

&emsp;&emsp;进一步验证需记录 raw 满载丢帧数、队列占用、每帧处理墙钟与线程 CPU 时间，以及解码、clone、共享复制、锁和日志各段的耗时分布，关注最长停顿而非只看平均值。线程 CPU 时间可使用 `CLOCK_THREAD_CPUTIME_ID`；必要时通过 `/proc/<父进程PID>/task/<处理线程TID>/wchan` 和 `strace -f -tt -T -e trace=futex,write,ioctl -p <父进程PID>` 查等待位置。不要用每帧同步打印来测量，否则测量本身可能成为瓶颈；可累计到内存，低频输出摘要，最后关闭跟踪复测。若怀疑诊断输出，应保留相同计数方式再比较日志开关，不能关掉日志后把“看不到 FPS”当成性能恢复。

&emsp;&emsp;面试中可以这样回答：MJPEG 省掉了软件 JPEG 编码，但当前处理线程仍串行承担按需解码和 BGR 分发，HTTP 压缩帧也要等这些步骤完成后才能入队。CPU 平均只有一半不能独立证明瓶颈；若确认整机持续空闲且处理线程持续有活可做，就必须检查为何它没有运行。持续 `FPS < CAP` 时，先用 raw 丢帧计数闭合数据，再用分段计时确定是计算、阻塞、突发还是统计问题。后续可评估先转发 JPEG、再由独立支路按需解码，但要明确丢帧策略、帧关联与内存上限；本次只记录分析，没有变更流水线。

### 程序加入统计后，如何用日志验证 CAP 与 FPS 的差距

&emsp;&emsp;程序现已增加约一秒窗口的 `[Pipeline]` 与 `[Timing]`，使用 `CAM_DEBUG=1` 显式开启输出。先核对 `RAW_TOTAL=累计入队/累计取出/累计丢弃`，累计入队应等于累计取出、累计丢弃与 `RAW_DEPTH` 之和；再观察窗口 `RAW_DROP` 是否持续增加，确认 CAP 与处理帧数差额是否被 raw 队列丢弃。`JPEG_DROP` 是处理完成后的输出丢帧，不能算成 CAP 到 FPS 之间的丢帧。

&emsp;&emsp;`[Timing]` 每项为 `次数/平均毫秒/最大毫秒`。先看 `WAIT` 与 `WORK` 区分取帧等待和处理过程，再看 `DECODE`、`FACE_SUBMIT`、`LCD_PUBLISH`、`JPEG`、`PUSH` 定位耗时阶段。`AGE` 是应用排队年龄；`REPORT_PREV` 是上一轮统计及输出自身的耗时，可识别诊断日志造成的停顿。平均值较低但最大值很高，仍可能导致小队列在短时间内溢出。

&emsp;&emsp;`THREAD_CPU` 只计处理线程，`SYS_IDLE` 才是整机空闲比例；两者不能当作互补值，父进程其他线程、LCD 子进程和内核也在运行。对照纯转发、仅 LCD、仅人脸三种配置，结合真实阶段次数和时间分布判断，不能只看旧的 `JPEG` 耗时。CPU、队列快照与墙钟存在采样边界偏差，应保留多个稳定窗口；完全无帧时报告不会定时触发。完整字段和运行命令见 [cam.md 的处理流水线诊断统计](cam.md#处理流水线诊断统计)。这些诊断已实现，板端根因仍待实际日志验证。
