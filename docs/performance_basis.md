## 性能评估依据与测量边界

&emsp;&emsp;本文对应当前 i.MX6ULL 摄像头、LCD 和 HTTP 流水线，保留现有方案，只解释各项性能如何测量、能证明什么以及不能证明什么。技术总览见 [cam.md](cam.md)，方案历史见 [record.md](record.md)，相关问答见 [interview.md](interview.md)。本文没有新增板端实测结果。

## 评估的基本方法

&emsp;&emsp;每项指标都需要明确事件、时间范围和单位。吞吐量通常是“成功完成的事件数 / 实际窗口秒数”；单次耗时是“结束时刻 − 开始时刻”；CPU 利用率是“实际 CPU 执行时间 / 墙钟时间”。采集成功、处理完成、绘制返回、硬件扫描和浏览器呈现是不同事件，不能统一当作视频 FPS。

&emsp;&emsp;当前处理窗口由 [src/main.cpp](../src/main.cpp) 的 `encodeLoop()` 在完成一帧后检查：超过约一秒才报告，因此不是严格的一秒定时器，无帧或线程长期阻塞时也不能保证按秒输出。阶段计时使用 `std::chrono::steady_clock` 单调时钟，不受系统日历时间调整影响。

| 依据类型 | 当前获取方式 | 适合回答的问题 |
| --- | --- | --- |
| 软件事件计数 | 成功取帧、处理完成、绘制成功、队列入出与丢弃时累加 | 每一级完成多少工作，哪里丢帧 |
| 墙钟耗时 | 单调时钟在阶段前后取差 | 一次操作让流水线经过了多长时间 |
| CPU 执行时间 | `CLOCK_THREAD_CPUTIME_ID` | 处理线程实际占用了多少 CPU 时间 |
| 整机 CPU ticks | 两次读取 `/proc/stat` | 系统总体空闲情况 |
| 硬件事件与信号 | LCDIF VSYNC、帧完成事件，外部测量 VSYNC | 显示控制器的扫描周期和同步行为 |
| 外部可见结果 | 同一画面中的源端计时器、LCD、浏览器及高速录像 | 新图是否真正呈现，端到端延迟是多少 |

## 数据流与测量位置

```text
相机曝光、内部处理、USB 与内核缓冲
    ↓ 成功取帧，写入应用时间戳，CAP 计数
raw 有界队列：RAW_IN / RAW_OUT / RAW_DROP / RAW_DEPTH
    ↓ raw.take()：WAIT；取出时计算 AGE
主处理：DECODE → FACE_SUBMIT → LCD_PUBLISH → HEALTH → JPEG → PUSH
    │    WORK 覆盖取帧后到 JPEG 入队完成，FPS 在该步骤后计数
    ├── 人脸线程：后台检测，未计入 FACE_SUBMIT 的全过程
    ├── LCD 共享槽：信号量通知，子进程取最新 READY 帧
    │       ↓ 缩放、像素打包、显存写入、启用时的同步翻页
    │       display.render() 成功：LCD_FPS 计数，累计 LCD 耗时
    │       ↓ LCDIF 扫描 → 面板呈现
    └── jpeg 有界队列 → 主线程发布最新 JPEG → HTTP → 浏览器呈现
```

&emsp;&emsp;这些支路异步运行，各自可能抽样或跳过旧帧。主处理完成一帧，并不意味着 LCD 和所有 HTTP 客户端都完成了同一帧。

## 吞吐量与显示耗时

| 字段 | 事件来源与计算方式 | 能说明什么及边界 |
| --- | --- | --- |
| `CAP` | `captureLoop()` 成功取得应用帧后，`capturedFrames` 加一；窗口增量 / 窗口秒数 | 应用收到帧的速率；不是曝光次数，也不是 V4L2 格式表声明的上限 |
| `FPS` | 主处理完成 JPEG 入队步骤后，`statsFrames` 加一；完成数 / 窗口秒数 | 主处理吞吐；不保证后续队列未丢帧，也不代表浏览器已经显示 |
| `LCD_FPS` | LCD 子进程的 `display.render()` 成功返回后加一；读取并清零的完成数 / 主处理窗口秒数 | 应用绘制完成率；不是严格的面板扫描频率或新图呈现率 |
| `LCD` | 围绕 `display.render()` 记录墙钟时间，累计耗时 / 成功完成数 | 包含缩放、打包、写显存及内部实际发生的同步等待；不含此前等新帧和后面的统计面板绘制 |
| `JPEG` | 围绕 MJPEG 字节移动或 YUYV 软件 JPEG 编码计时，累计耗时 / 处理帧数 | MJPEG 时主要是复用压缩数据的成本，不包含相机内部编码，也不包含前面的按需解码 |

&emsp;&emsp;LCD 计数与耗时在 [src/lcd_process.cpp](../src/lcd_process.cpp) 的 `renderLoop()` 累加，由 `takeRenderStats()` 在共享互斥锁内读取并清零。LCD 快照与主线程窗口边界不是完全同时取得，单个短窗口可能有边界误差，应比较稳定的连续多个窗口。

## LCD 的垂直同步与实际呈现

### 扫描频率的依据

&emsp;&emsp;本项目的 RGB LCD 由 LCDIF 按时序持续扫描显存，输出像素时钟、同步信号和像素数据。应用没有更新显存时，控制器仍可以重复扫描原来的图像。i.MX6ULL 的 LCDIF 引脚和电气时序见 [NXP 数据手册的 LCD Controller Parameters](https://www.nxp.com/docs/en/data-sheet/IMX6ULLCEC.pdf)。

&emsp;&emsp;VSYNC 标记帧周期边界。示波器或逻辑分析仪测量连续同极性有效边沿，例如只数上升沿，可以得到硬件输出的扫描周期；不能把上升沿和下降沿都当作一帧。

```text
Htotal = 1024 + 水平前肩 + 水平后肩 + 水平同步宽度
Vtotal = 600  + 垂直前肩 + 垂直后肩 + 垂直同步宽度

预期扫描频率 Hz = 实际像素时钟 Hz / (Htotal × Vtotal)
测量扫描频率 Hz = 连续同极性 VSYNC 边沿间隔数 / 对应时间秒数
```

&emsp;&emsp;1024×600 是有效显示区域，不能省略消隐区计算扫描频率。设备树提供目标时序，实际时钟还受时钟树分频与取整影响，外部测量可验证真实输出。这里只给出计算方法，没有宣称当前面板实测为 60 Hz。

### 扫描、绘制与新图呈现的区别

| 指标 | 依据 | 示例含义 |
| --- | --- | --- |
| 硬件扫描频率 | 连续 VSYNC 周期或持续硬件帧事件 | 假设为 60 Hz，表示每秒扫描约 60 次 |
| 应用绘制完成率 | `display.render()` 成功返回计数 | 假设 `LCD_FPS=10`，表示每秒约完成十次调用 |
| 不同新帧的实际呈现率 | 帧号与硬件生效页、扫描周期关联，必要时外部录像核验 | 每秒完整呈现多少张不同的新图，当前没有严格计数 |

&emsp;&emsp;假设面板扫描为 60 Hz，应用每秒提供十张新图，期间可以重复扫描旧图。此时不能把视频更新速度说成 60 FPS。反过来，即便应用写入很快，多次提交也可能被合并、跳过，或在单缓冲下产生撕裂。

### 当前同步实现的证据和限制

&emsp;&emsp;[src/framebuffer.cpp](../src/framebuffer.cpp) 在双缓冲路径先绘制后台页，再尝试 `FBIO_WAITFORVSYNC`，随后调用 `FBIOPAN_DISPLAY`。[drv/lcd_drv.c](../drv/lcd_drv.c) 将目标地址写入 `NEXT_BUF`，有 IRQ 时等待通用帧完成事件，VSYNC 等待与帧完成等待由不同 completion 唤醒。

&emsp;&emsp;当前驱动未逐帧核对 `CUR_BUF` 是否等于提交的目标地址，因此 ioctl 返回与目标帧完整可见之间仍有测量边界。单缓冲、无 IRQ、同步不支持和翻页失败回退时，绘制成功尤其不能证明整张新图已经完整显示。控制器事件也不能直接证明面板像素的光学响应完成。

&emsp;&emsp;当前驱动只在等待期间启用对应中断，所以不能直接用 `/proc/interrupts` 的增长速度代表完整的扫描频率。若以后加入硬件扫描统计，需要持续采集所选帧事件、处理状态清除与漏计问题，并控制统计开销；外部测量 VSYNC 则可独立核验输出时序。

&emsp;&emsp;此前“单次 LCD 绘制约 100 ms，因此实际可见约 10 FPS”的说法应按估算理解：`1000 / 100 ≈ 10` 只是该路径持续有帧时的处理能力估算。等新帧、统计绘制和调度会影响完成率，实际完成次数看 `LCD_FPS`，严格的新图呈现率需另外验证。

## 阶段耗时的测量依据

&emsp;&emsp;`[Timing]` 每项格式为 `调用次数/平均毫秒/最大毫秒`。例如 `DECODE=10/5.200/22.000` 表示该窗口调用十次，平均 5.2 ms，最慢 22 ms；没有调用时输出 `0/0.000/0.000`。

| 字段 | 开始与结束边界 | 解释限制 |
| --- | --- | --- |
| `WAIT` | 调用 `raw.take()` 前到成功返回后 | 包含等数据和队列锁等待，不能单独证明摄像头慢 |
| `AGE` | 采集线程记录的应用时间戳到处理线程取出该帧 | 表示应用内排队年龄，不包含曝光、相机内部和此前的驱动等待 |
| `WORK` | 取帧后到 JPEG 入队步骤完成 | 包含下列多个子阶段，不含取帧等待、后续局部对象析构及周期报告 |
| `DECODE` | MJPEG `imdecode` 前后，或 YUYV 校验与 BGR 转换前后 | MJPEG 只在 LCD 或人脸需要 BGR 时执行，平均值按实际调用数计算 |
| `FACE_SUBMIT` | 人脸任务提交前后 | 包含抽样判断、所需 clone 和提交锁，不是后台检测耗时 |
| `LCD_PUBLISH` | 共享 BGR 帧发布前后 | 包含共享锁、复制和信号量通知，不含子进程绘制 |
| `HEALTH` | LCD 子进程健康检查前后 | 包含 `waitpid(WNOHANG)`，不代表绘制完成 |
| `JPEG` | 压缩数据移动或软件编码前后 | 与 `[Stats] JPEG` 覆盖相同主体，附带次数及最大值；计时边界有少量差异 |
| `PUSH` | JPEG 队列 `push()` 前后 | 包含队列锁、必要的丢旧与入队，不包含网络发送 |
| `REPORT_PREV` | 上一次完整报告操作前后 | 包含快照、LCD 统计访问、字符串生成和日志输出，记入下一窗口，首窗口为零 |

&emsp;&emsp;墙钟时间包含阶段内被抢占或阻塞的时间，因此“某函数经过 100 ms”不等于“占用 CPU 100 ms”。`WORK` 已经包含子阶段，`AGE` 也与等待过程重叠，不能将全部字段相加。某阶段的窗口累计成本可由调用次数乘平均耗时得到；跨线程、跨进程的时间可能重叠，也不能相加当作端到端延迟。

## 队列积压与丢帧的依据

&emsp;&emsp;[include/bounded_queue.hpp](../include/bounded_queue.hpp) 在队列原有互斥锁内同步维护元素和累计计数，`stats()` 返回一致快照。当前 raw、jpeg 队列容量均为 3，满载时丢最旧帧。

| 字段 | 测量依据 |
| --- | --- |
| `WINDOW / N` | 实际统计窗口秒数 / 主处理完成帧数 |
| `RAW_IN / RAW_OUT / RAW_DROP` | 两次快照之间的成功入队 / 成功取出 / 满载丢弃增量，单位为帧，不是每秒速率 |
| `RAW_DEPTH` | 读取快照时仍在队列中的帧数，不含已经取出正在处理的帧 |
| `RAW_HIGH` | 队列自创建以来的最高水位，不是本窗口最高值 |
| `RAW_TOTAL` | 累计成功入队 / 成功取出 / 满载丢弃，使用同一快照核对守恒 |
| `JPEG_DROP / JPEG_DEPTH` | JPEG 输出队列窗口满载丢弃数 / 快照时的深度，不包含客户端跳过最新帧之外的旧图 |

```text
同一队列快照：累计入队 = 累计取出 + 累计满载丢弃 + 当前深度
```

&emsp;&emsp;关闭后被拒绝的入队不增加计数，失败取出也不增加取出数。`CAP` 自增与 raw 入队不是同一原子操作，不应要求单个窗口的 `CAP × WINDOW` 严格等于 `RAW_IN`；守恒检查应使用同锁快照。队列深度也不能单独给出精确延迟，实际排队情况应结合 `AGE`。

## CPU 利用率的依据

```text
THREAD_CPU % = 处理线程 CPU 时间增量 / 窗口墙钟时间 × 100
SYS_IDLE %   = /proc/stat 的 idle ticks 增量 / 总 CPU ticks 增量 × 100
```

&emsp;&emsp;`THREAD_CPU` 使用 `CLOCK_THREAD_CPUTIME_ID`，包含采样范围内的线程用户态和内核态执行时间，不包含 LCD 子进程、人脸线程及 HTTP 线程。`SYS_IDLE` 是整机汇总，包含其他任务和中断负载的影响，当前实现不把 iowait 合并到 idle。读取不可用时输出 `n/a`；多核开发机的整机平均值也不能直接当作单个核心空闲率。

&emsp;&emsp;`top` 可补充父子进程与线程 CPU 观测，但采样窗口和统计口径需要一致。CPU 没跑满可能是供帧不足、锁等待、硬件等待或调度，不能仅凭占用率指定根因；运行中的内存访问停顿通常仍计入 CPU 时间，不能直接解释为睡眠。

&emsp;&emsp;例如某段墙钟耗时 100 ms，而同一线程同一时间段的 CPU 时间只增加 20 ms，其余时间可能在等待或被抢占。当前 `THREAD_CPU` 是整窗口指标，不能据此计算每个子阶段的 CPU 消耗；要定位具体锁或 ioctl，需要进一步针对该线程跟踪。

## 从现象到瓶颈结论

| 观测现象 | 当前能支持的判断 | 进一步验证 |
| --- | --- | --- |
| 稳定多窗口 CAP 高于 FPS，RAW_DROP 持续增长 | 输入队列丢帧，主处理消费跟不上供帧 | 比较 WORK、各子阶段累计耗时、CPU 与报告开销 |
| JPEG 接近零，但 WORK 较高 | 压缩字节复用便宜，整条处理路径仍有成本 | 检查 DECODE、FACE_SUBMIT、LCD_PUBLISH 等 |
| DECODE 累计成本高 | 解码是重要耗时候选 | 对照纯 MJPEG 转发、仅 LCD、仅人脸，固定其他条件 |
| LCD 耗时高，CPU 仍有空闲 | 显示路径经过时间长，CPU 百分比不足以确定根因 | 拆分缩放、打包、显存复制、VSYNC 和翻页等待 |
| WAIT 较高 | 取帧步骤包含较多等待 | 独立验证摄像头输出，再检查队列锁与调度 |
| WORK 最大值显著高于平均值 | 处理存在突发停顿 | 对照丢帧、调度、锁和系统调用时间 |
| REPORT_PREV 较高 | 诊断输出自身可能干扰流水线 | 减少输出或比较关闭日志时的行为 |
| 双缓冲后撕裂减少，LCD 耗时未明显降低 | 同步与画面完整性可能改善，吞吐收益尚未体现 | 继续测量各阶段，不能直接认定是显存带宽瓶颈 |

&emsp;&emsp;性能优化需要在同条件下做对照，并同时观察成本、吞吐、丢帧和延迟。增加队列容量只改变缓冲与丢帧特征，不增加算力；LCD 抽样减少供帧与解码次数，不能宣称单次绘制变快；双缓冲主要改善页面所有权与撕裂，实际速度收益要实测。

## 板端使用与验证

&emsp;&emsp;以下构建命令在工程根目录执行，不在 `docs/` 内执行。文档整理没有改变构建方式。

```sh
make -f Makefile.arm package_arm
```

&emsp;&emsp;部署后，在包含程序、`lib` 与 `assets` 的板端目录运行，记录稳定的连续多个窗口；摄像头节点按实际设备调整。

```sh
CAM_DEBUG=1 ./cam_server_arm --device /dev/video1 --format mjpeg \
  --fb /dev/fb0 --no-touch --no-face --lcd-interval 1 \
  > /tmp/cam-stats.log 2>&1
```

&emsp;&emsp;预期输出 `[Stats]`、`[Pipeline]` 和 `[Timing]`，用上述口径解释每一项。对照纯转发时用 `--no-lcd --no-touch --no-face`；人脸对照需启用分析并确认模型加载成功。固定格式、分辨率、曝光、光照、LCD 抽样和客户端数量，避开启动窗口；串口输出、文件写入和持续运行的 `top` 都可能干扰测量。

&emsp;&emsp;独立测量摄像头时，先停止占用该摄像头的应用，再执行采集测试。格式表和 `--get-parm` 反映能力或协商值，持续采集测得的速率才是该条件下的实际交付能力。

```sh
v4l2-ctl -d /dev/video1 \
  --set-fmt-video=width=640,height=480,pixelformat=MJPG \
  --set-parm=30 --stream-mmap --stream-count=300
```

&emsp;&emsp;用 `fbset -fb /dev/fb0 -i` 核对模式和虚拟高度，用 `dmesg` 排查 LCDIF 超时或错误，用示波器或逻辑分析仪核对 VSYNC。要测端到端延迟，可让相机拍摄计时器，并在同一外部录像中同时拍到计时器与 LCD，比较同一时刻的读数；浏览器可用同样方法。结果受录像帧间隔、曝光和扫描影响，不能把 `LCD` 或 `AGE` 单独当作完整端到端延迟。

## 学习指南与证据范围

&emsp;&emsp;建议按“V4L2 取帧与时间戳 → 有界队列与快照守恒 → 单调时钟和线程 CPU 时钟 → 共享内存与信号量 → framebuffer 页翻转 → LCDIF VSYNC 与帧完成 → HTTP 和浏览器呈现”的顺序阅读代码。需要掌握 Linux 进程与线程同步、OpenCV 解码与缩放、fbdev、RGB LCD 时序，以及吞吐量、延迟和 CPU 利用率之间的区别。

&emsp;&emsp;当前软件统计能证明应用边界内的完成次数、耗时与丢帧，不能替代连续硬件事件采集和外部呈现验证。后续若要增加严格上屏计数，应建立帧号、目标页地址和硬件生效状态的关联；若要细分显示瓶颈，再增加 LCD 各阶段测量。上述内容是后续验证方向，本次没有修改运行方案或加入这些统计。
